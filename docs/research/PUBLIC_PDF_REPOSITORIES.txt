PDF STUDIO — ALL PUBLIC REPOSITORIES PREVIOUSLY RECOMMENDED
===============================================================
Verified links / repository metadata reviewed: 2026-11-15
Product repository: https://github.com/renoukhan39-bit/pdfstudio
Authoritative scope: docs/ACTIVE-SCOPE.md, docs/IMPLEMENTATION-CHECKLIST.md, AGENTS.md

IMPORTANT: THIS IS A RESEARCH AND INTEGRATION LIST, NOT A LIST OF IMPORTED CODE.
Only Stages A–D are active. Stage E (AI and advanced automation) and
Stage F (accounts, billing, collaboration, enterprise) are FROZEN.
The existing PDF Studio FastAPI / pypdf / worker + Gotenberg foundation is
the product of record. DO NOT blindly merge multiple complete PDF websites.
For each upstream dependency, audit its actual pinned version, LICENSE, NOTICE,
transitive dependencies, fonts, model weights, security and commercial SaaS
permissions before copying, deploying or redistributing anything.
A public repository is NOT automatically freely reusable in a proprietary app.

STATUS KEY
INTEGRATED     Already used in PDF Studio (specific functionality, not entire upstream).
NEXT           Approved candidate for the next focused A–D integration.
EVALUATE       Try only if a test shows a relevant feature gap.
STUDY ONLY     Reference architecture/UX; do not copy whole project.
HOLD E/F       Outside our current approved A–D scope.
RESTRICTED     Do not copy/use commercially without an approved license review.
REFERENCE      An engine/service/project to learn from; no import requirement.

PART 1 — HIGH-VALUE A–D ENGINES / SELECTED REUSABLE COMPONENTS
---------------------------------------------------------------
01. Gotenberg — gotenberg/gotenberg
    https://github.com/gotenberg/gotenberg
    GitHub license metadata: MIT (review bundled engine dependencies).
    STATUS: INTEGRATED; NEXT expand its validated adapter.
    Why: private HTTP PDF processing API; DOCX-to-PDF implemented and CI tested.
    Reuse for: XLSX/PPTX/HTML-to-PDF, PDF rendering/other supported operations
    only after individual output and security tests.
    Action: pin approved Gotenberg 9 patch release/container digest. No need
    to copy the Gotenberg Go server into PDF Studio.

02. Mozilla PDF.js — mozilla/pdf.js
    https://github.com/mozilla/pdf.js
    Metadata: Apache-2.0. STATUS: NEXT (Stage C).
    Why: robust PDF viewing, thumbnails, zoom, text selection and search.
    Limitation: does NOT provide a complete native existing-content editor.

03. pdf-lib — Hopding/pdf-lib
    https://github.com/Hopding/pdf-lib
    Metadata: MIT. STATUS: EVALUATE (Stage C).
    Why: browser PDF creation, page objects, new text/images, forms.
    Note: latest upstream push seen 2024-07-17; audit maintenance/bugs.
    Limitation: cannot generally rewrite existing arbitrary PDF page text.

04. OCRmyPDF — ocrmypdf/OCRmyPDF
    https://github.com/ocrmypdf/OCRmyPDF
    Metadata: MPL-2.0 (dependencies have their own licenses).
    STATUS: NEXT after conversions (Stage D).
    Why: OCR text layers and scan deskew. Keep in isolated worker.

05. pyHanko — MatthiasValvekens/pyHanko
    https://github.com/MatthiasValvekens/pyHanko
    Metadata: MIT. STATUS: NEXT later in Stage D.
    Why: cryptographic PDF signing, PAdES and signature validation.
    Warning: visual/drawn signatures and cryptographic signatures differ;
    signing keys, certificate validation and jurisdiction rules require care.

06. qpdf — qpdf/qpdf
    https://github.com/qpdf/qpdf
    Metadata: Apache-2.0. STATUS: EVALUATE only for proven gaps.
    Why: structural PDF handling/encryption/merge and repair-related tasks.
    Avoid duplicating existing pypdf or Gotenberg operations.

07. Apache PDFBox — apache/pdfbox
    https://github.com/apache/pdfbox
    Metadata: Apache-2.0. STATUS: REFERENCE / optional Stage D specialist.
    Why: Java PDF parsing/manipulation, form/metadata operations.
    Caution: a Java service adds maintenance and deployment weight.

08. pdfcpu — pdfcpu/pdfcpu
    https://github.com/pdfcpu/pdfcpu
    Metadata: Apache-2.0. STATUS: EVALUATE only if needed.
    Why: Go PDF tooling, page operations and optimization alternatives.
    Avoid adding a redundant PDF engine without a benchmark.

09. pdfme — pdfme/pdfme
    https://github.com/pdfme/pdfme
    Metadata: MIT. STATUS: EVALUATE (Stage C/D forms/templates).
    Why: visual PDF templates and document generation.
    Important: templates are not general existing-document text editing.

10. React Konva — konvajs/react-konva
    https://github.com/konvajs/react-konva
    Metadata: MIT. STATUS: EVALUATE (Stage C).
    Why: selection handles, canvas annotations, shapes and object positioning.
    Note: canvas graphics do not automatically persist as correct PDF objects.

11. Tesseract OCR — tesseract-ocr/tesseract
    https://github.com/tesseract-ocr/tesseract
    Metadata: Apache-2.0. STATUS: REFERENCE / OCRmyPDF dependency.
    Why: OCR engine; use through OCRmyPDF where appropriate.
    Include model-language-data and license review for Hindi/Punjabi OCR.

12. LibreOffice core — LibreOffice/core
    https://github.com/LibreOffice/core
    Metadata: GPL-3.0 on GitHub; upstream licensing is nuanced.
    STATUS: REFERENCE / Gotenberg dependency, NOT direct source merge.
    Why: real Office document rendering/conversion behind Gotenberg.
    Do not copy LibreOffice code into proprietary PDF Studio.

THE EXACT INTEGRATION ORDER FOR STAGES A–D
-----------------------------------------
A. Keep existing 15-tool PDF Studio, fix release/security/licensing gates and
   preserve current GitHub CI. No wholesale imported website.
B. Expand the existing private Gotenberg adapter for XLSX, PPTX, HTML and
   image conversions where outputs pass fidelity tests; use pypdf for
   existing working page tools. Avoid redundant engines.
C. Add PDF.js viewer; evaluate pdf-lib and Konva for specific annotation/forms
   use. Choose native existing-text engine only after commercial license and
   underlying-content edit tests.
D. Add OCRmyPDF, signature verification with pyHanko, true secure redaction,
   archival, comparison and specialist engines only for proven gaps.
E/F. FROZEN. Do not scaffold or implement.

CODEX/COST CONTROL
------------------
- Study existing app and dependencies BEFORE writing any code.
- Reuse maintained engines; do NOT rebuild converters, OCR or renderers.
- One feature / one test corpus / one reviewable PR.
- Use GitHub CI for Docker/Playwright testing first; reserve Astra for a
  reproducible blocker with logs and failing acceptance tests.
- Never silently reduce test coverage, disable checks or claim that
  browser overlays are secure redaction/native content editing.
- Owner approves license/SDK expenses, data retention, hosting and launch.
