# Core PDF toolkit

The website and API now expose fifteen prototype tools (14 PDF operations plus DOCX-to-PDF conversion). This is an expanded local-development prototype, not the complete Acrobat/Sejda roadmap or a publicly hardened service.

| Tool | API | Options and output |
| --- | --- | --- |
| Merge | POST `/api/tools/merge` | Multipart `files`, 2–10 PDFs; combined PDF |
| Split | POST `/api/tools/split` | `pages`: `1-3;4-6`; blank creates one PDF per page; ZIP |
| Extract | POST `/api/tools/extract` | `pages`: `3,1-2`; selected pages in requested order |
| Delete | POST `/api/tools/delete` | `pages`: `2,4`; all other pages retained |
| Reorder | POST `/api/tools/reorder` | `pages`: every page exactly once, such as `3,1,2` |
| Rotate | POST `/api/tools/rotate` | `pages`: blank means all; `angle`: `90`, `180`, `270` clockwise |
| Compress | POST `/api/tools/compress` | Lossless content stream compression and object deduplication; original returned if no size saving |
| Metadata | POST `/api/tools/metadata` | `title`, `author`, `subject`, `keywords`; document-info fields only |
| Extract text | POST `/api/tools/text` | Optional `pages`; UTF-8 plain text, with page labels |
| Protect | POST `/api/tools/protect` | `password`: 8–256 characters; AES-256 encrypted PDF |
| Unlock | POST `/api/tools/unlock` | `password`: known password; unencrypted PDF |
| Word to PDF | POST `/api/tools/docx-to-pdf` | Single DOCX `file`; requires Docker Compose with private Gotenberg 9; output PDF |

Except merge, send one multipart `file` and a JSON-object string in `options`; DOCX-to-PDF needs only `file`. All option values are strings. Page numbers are one-based, ascending ranges are accepted, and duplicate selection within a group is rejected. Output names are generated by the server, never derived from uploaded filenames.

```sh
curl -f http://127.0.0.1:8000/api/tools/extract \
  -F 'file=@synthetic.pdf' -F 'options={"pages":"3,1"}' --output selected.pdf
```

## Workspace

Choose any working tool from the catalog or dropdown. Upload, configure, process and download. PDF results up to 8 MiB can become the input for the next operation with **Use result in another tool**. This is a browser-session convenience; closing/reloading the page clears the workspace. Password fields clear after processing and switching tools. Downloads remain on the user's device; the application does not manage them.

## Limits and trust boundaries

- 8 MiB per input PDF, 40 MiB combined input, 200 pages per operation; split groups also have a cumulative 200-page ceiling.
- Raw HTTP body cap: 41 MiB, with a 30-second upload deadline. Output: up to 40 MiB; split also limits the uncompressed total.
- PDF parsing/transformation runs in a child process, not the API event loop. Two processing slots per API process; excess requests receive 503 with Retry-After.
- Every child has a 25-second wall deadline. Linux children additionally have 20 CPU seconds, 768 MiB address space, and core dumps disabled. Other operating systems retain wall time and slot limits but not Linux resource limits.
- Temporary upload spools close on all exit paths. Child inputs/results use pipes. No document database or intentional server-side retention is added.
- Processes still inherit host filesystem/network permissions. This is **not** a hostile-code sandbox. Container namespace/egress isolation, global ingress quotas, production authentication/rate limits and retention audits remain required before public deployment.

## Fidelity and honest boundaries

Generated PDFs are reopened and page counts verified; tests inspect page order, rotations, text and encryption. Existing forms, bookmarks, complex annotations, multilingual layout, accessibility tags and signatures still need a larger fidelity corpus. Changing a signed PDF may invalidate its signatures.

Compression is lossless and is not guaranteed to shrink every PDF. Metadata editing is not hidden-data sanitization. PDF text extraction does not OCR scanned pages and reading order depends on the source. Encryption does not provide certificate signatures. Uploading a password is server-side processing; use TLS in any network deployment.

Native text editing, OCR, **reverse PDF-to-Office conversions**, image rendering, secure redaction and digital signing remain incomplete. DOCX-to-PDF uses Gotenberg in Compose and has a synthetic smoke test; real-world conversion fidelity requires further testing. Accounts, billing and AI are frozen in Stages E/F. Original-code licensing is still an owner decision.

## Tests

`python -m pytest -q --cov=app --cov-branch --cov-report=term-missing --cov-fail-under=85`

The same command runs in GitHub Actions on Python 3.11, 3.12 and 3.13. A failed assertion, missing coverage, dependency advisory, packaging failure or container failure fails `CI required`. No advisory suppression or weaker coverage threshold was added.

## Added page tools

- POST `/api/tools/page-numbers`: optional `pages`; printed `page / total` at the visible footer.
- POST `/api/tools/watermark`: `text` (1–120 printable ASCII characters), optional `pages`; translucent diagonal overlay.
- POST `/api/tools/crop`: `margin` in PDF points (0–500), optional `pages`; shrinks the crop box equally on all sides. Hidden content is retained and recoverable; never use cropping as redaction.

All use multipart `file` and JSON `options` like other tools. Numbering and watermarks are positioned relative to the visible crop box, including rotated/cropped pages. Crop and overlays can invalidate signatures.

## Isolated development deployment

Use `docker compose up --build -d --wait` and open http://127.0.0.1:8000. This runs a dedicated worker with internal networking and filesystem/resource restrictions. Direct `uvicorn app.main:app` retains local child-process mode; use it only for development. See [Deployment](DEPLOYMENT.md). Active raw uploads are limited to two per service process; excess requests receive 503 before parsing.
